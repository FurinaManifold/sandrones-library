# Sandrone's Library — 架构设计

> **一句话**：以 mathlib4 为地基，建立一个"LLM 友好且绝对严格的数学大厦"——
> 把**人类思维脉络**、**机器可验证的 Lean 形式化**、**面向 LLM 的双语解释**三者绑定为一条条可扩展的"事实条目"。

## 0. 动机（为什么 2024 年做不了，2026 年可以做）

- 2024 年：模型（如 R1 之前的 DeepSeek）没有成形的推理能力（链式思维），
  既无法*从零*构造 Lean 证明步骤，也无法把人类写的数学答案*转写*为可编译的 Lean 代码。
  因此"以 Lean 为载体的、LLM 可维护的数学库"是空中楼阁。
- 2026 年：具有链式思维的模型可以：读懂一段人类数学推理 → 逐句映射到 Lean 陈述 →
  依据 Lean 编译器的报错迭代修复。**转写与证明不再是瓶颈，知识组织才是瓶颈。**
- 结论：现在是建这个库的正确时间点。我们要解决的问题从"模型会不会证明"
  变成"如何组织知识，使模型的证明/转写能力可以**增量累积**"。

## 1. 定位与设计原则

### 1.1 与 mathlib 的关系

- Sandrone's Library **不是**另一个 mathlib。它**完全依赖** mathlib 作为地基。
- mathlib 是"编译器视角"的库：命名、模块划分、定理粒度服务于证明自动化和 API 复用，
  对 LLM 不友好（搜索困难、缺少人类动机、命名晦涩）。
- Sandrone's Library 在 mathlib 之上叠加**叙事层**：每个数学事实用人类思维脉络讲清楚
  "为什么、直觉是什么、怎么证明、错在哪"。
- 数学大厦的地基（存在性、实数构造、拓扑等基础理论）直接引用 mathlib，
  叙述层负责把它变成"可教给 LLM 和人类的知识"。

### 1.2 与 benchmark 的关系

- miniF2F / ProofNet / PutnamBench：给定题目，让模型证明 —— **评测**。
- Sandrone's Library：已验证的证明 + 思维脉络 + 双语解释 —— **知识库**。
- 但"可扩展性"必须有可量化指标，因此附带一个 **ingestion benchmark**：
  随机抽取论文/教材结论，看模型能否按 [纳入协议](INGESTION_PROTOCOL.md) 完成纳入。
  这是"可扩展性"的可操作定义。

### 1.3 大一新生视角（知识的组织原则）

> 身份设定：**这个库的"读者/维护者"是一个刚入学的数学系大一新生。**
> mathlib 是一本包罗万象、但一个定理都看不懂的教科书；
> 我们"读"它的方式，就是**把大一新生读得懂、用得上的定理逐条纳入知识库，
> 保证之后可以检索到、拿来调用**。

由此产生三条组织原则：

1. **按人类学习路径组织**，而非按 mathlib 的模块划分。
   库的骨架 = 课程大纲（数学分析 → 高等代数 → 解析几何 → … → 后续课程），
   每个课程是一棵"章节 → 节 → 条目"的树。
2. **"读"的定义 = 纳入 + 可检索 + 可调用**。一个定理没有被注册进库、
   没有叙述层、不能被别的条目引用，就等于没读过。
3. **学习从一年级开始**。不管最后要覆盖到多深的数学，
   当下的建设顺序严格跟随大一课程：先集合论与实数，再序列、函数、连续性……逐章推进。

### 1.4 多版本机制（价值由调用量筛选）

同一数学结论常存在多个版本：不同教材的人话陈述（Rudin / 卓里奇 / 华东师大 / 陈纪修 …），
以及 mathlib 中的形式化版本。

- **允许、鼓励多版本共存**。每个版本是一个独立条目，共享一个 `family`（事实家族 id），
  各自带 `variant` 标签（来源）。
- **版本之间不合并、不裁决**。谁更有价值，由**实际调用量**决定：
  `registry` 统计每条目的 `dependedOnBy` 数量——被后续条目引用得越多的版本，
  就是对这个库越有价值的版本。这是库内的"自然选择"。
- 因此"人话版"与"mathlib 形式化版"可以互为独立条目，同一 family 下并存。

### 1.5 设计原则

| 原则 | 含义 |
|---|---|
| **严格性** | 所有形式化陈述必须通过 Lean 内核校验；"严格"不依赖人类或 LLM 的信任。 |
| **思维脉络** | 每个条目有从"人类动机"到"形式化证明"的完整推理链，而非孤立代码。 |
| **双语** | 每一条目 = Lean（机器可读）+ 自然语言（LLM/人类可读），二者可互相映射。 |
| **增量可扩展** | 新条目只依赖库中已有条目（依赖图），纳入有固定协议与自动验收。 |
| **可追溯** | 每个条目有 provenance（来源文章/书籍/章节/结论编号）。 |
| **防失真** | 宁可标注"未完成/待验证"，也不让 LLM 用流畅语言掩盖证据缺口（借鉴 math-example-atlas 的 `fact`/`derived`/`unresolved` 分类）。 |

## 2. 事实条目（Fact Entry）—— 核心数据结构

一个数学事实（定义 / 引理 / 命题 / 定理 / 例子）在库中是一个**双语条目**：

```
┌─────────────────────────────────────────────────────────┐
│  事实条目  <entry-id>                                     │
│                                                         │
│  A. 形式化层  (.lean)      ← 机器可校验，严格性在此保证      │
│     - 陈述（theorem/def）                                │
│     - 证明（策略脚本，带思路标注）                          │
│     - 元数据头（docstring：一句话陈述/直觉/依赖/来源）      │
│                                                         │
│  B. 叙述层  (docs/entries/<id>.md)   ← LLM/人类可读       │
│     - 动机：人类为什么要引入它                            │
│     - 直觉：核心洞见（可含反例/退化情形）                   │
│     - 思维脉络：清洗过的链式推理（为何选此策略）             │
│     - 自然语言 ↔ Lean 映射：每个符号/关键句怎么读           │
│     - 依赖：前置事实的人话版本                            │
│     - 应用与陷阱                                         │
│                                                         │
│  C. 元数据  (registry.json)   ← 机器可查                 │
│     - id, 依赖列表(premises), 来源(provenance),           │
│       状态(verified/pending/unresolved), mathlib引用      │
└─────────────────────────────────────────────────────────┘
```

### 2.1 条目 ID

`<域>.<子域>.<名字>`，如：

- `analysis.completeness.monotone-convergence`
- `analysis.fixedpoint.banach`
- `algebra.fields.quotient-ring`
- `settheory.choice.zorn`

ID 全局唯一，是叙述层与形式化层之间的"钩子"。

### 2.2 依赖图 = 人类思维脉络的形式化

- 每个条目声明 `premises: [entry-id...]`（它依赖的前置事实）。
- 所有条目的 premises 构成一个有向无环图。**这条依赖图就是"人类思维脉络"的机器形式**：
  一个定理的"怎么想出来的" = 它到地基（mathlib）之间的一条路径。
- 纳入新条目时**强制校验**：其 premises 必须全部已在库中（或本次一并纳入）。
- 这保证了知识增量构建：每加入一个结论，库的"可表达范围"扩大一块，且永远不悬空。

### 2.3 三种事实状态（防失真）

| 状态 | 含义 | Lean 层 |
|---|---|---|
| `verified` | 完整纳入，Lean 编译通过，叙述层与形式化层一致 | 有可编译代码 |
| `pending` | 正在纳入，依赖已满足但证明未完成 | 有陈述，证明留 `sorry`（必须显式标注） |
| `unresolved` | 陈述或来源存疑，暂不承诺正确性 | 无正式陈述，只有叙述层草稿 |

`registry.json` 只对 `verified` 条目做全库索引；`pending`/`unresolved` 单独列出，
**绝不静默混入**。

│   └── Algebra/

│   ├── INGESTION_PROTOCOL.md             # 纳入协议（核心工作流）
│   ├── SCHEMA.md                         # 条目字段规范（机器+人共读）

## 4. 分层职责与命名

- **模块组织按"人类学科"划分**（Analysis / Algebra / SetTheory / ...），
  而非 mathlib 的编译器风格。因为 LLM 与人类一样按学科检索。
- **定理命名优先"人话"**（`monotone-convergence`），并标注其对应的 mathlib 定理名
  （`tendsto_of_monotone_of_isBounded` 等），保证两套检索路径都通。
- **每个 .lean 文件顶部**：文件级 docstring 列出本文件所有条目 ID 与一句话陈述，
  让 LLM 通过 grep 就能导航。

## 5. LLM 友好性设计（为什么 LLM 能"学会"这个库）

1. **固定模板**：所有条目遵循同一 schema → 任意条目对 LLM 都是熟悉的 few-shot 样本。
2. **思维脉络可检索**：叙述层按"动机/直觉/思路/映射/依赖"分节，
   LLM 可按需检索，而非通读整篇。
3. **跨层映射表**（docs/mapping/）：把高频自然语言短语映射到 Lean 惯用法，
   显著降低转写歧义（如"在 0 附近"→ `∀ᶠ x in 𝓝[≠] 0` 等）。
4. **报错即反馈**：Lean 编译器的错误信息本身就是最强的监督信号，
   纳入协议把它设计为闭环（见 INGESTION_PROTOCOL.md §4）。
5. **双语原则**：叙述层以中文为主（贴近用户思维），并保留英文术语/陈述原文，
   便于模型检索与跨语种泛化。

## 6. 扩展性 = 纳入协议 + 纳入能力评测

- **纳入协议**：见 [INGESTION_PROTOCOL.md](INGESTION_PROTOCOL.md)。
  它把"给一篇文章的一个结论，纳入库中"分解为有明确产物的五步。
- **可扩展性的量化**：定期从论文/教材随机抽样 → 跑协议 → 统计
  通过率、时间、依赖复用率。这是本库"能不能持续长大"的体检指标。

## 7. 路线图

| 阶段 | 内容 | 验收 |
|---|---|---|
| Phase 0 | 环境 + 骨架 + 设计文档 + 协议 | 本仓库可 `lake build` 通过 |
| Phase 1 | Schema 定稿 + 3 个样板条目（含一个需要新定义/新引理链的）| 全流程人工走通，`audit.py` 通过 |
| Phase 2 | 协议工具化（new_entry / audit / registry 自动更新）| 纯脚本可完成一个"小条目"的注册 |
| Phase 3 | ingestion benchmark 上线（量化可扩展性）| 抽样结论的纳入通过率有基线 |
| Phase 4 | 从教材（如 Rudin / Zorich）与论文批量纳入 | 依赖图达到一定规模，覆盖一个学科主线 |
