# 1　项目定位：一座人能读、机器能检查的数学图书馆

**Sandrone’s Library 项目介绍**\
**自然语言与 Lean 的对应验证，以及论文形式化的 Multi-agent 工作流**

一个数学家读懂定理，通常需要知道：它为何出现，假设各自有什么作用，证明的关键转折在哪里，怎样用到下一道问题。本项目希望将这些解释与可以检查的 Lean 声明放在一起，让每次形式化都成为后续学习和研究能复用的知识。[S1、S13]

## DESIGN 的核心：按人的学习路径组织知识

`DESIGN.md` 以“数学系新生怎样逐步理解数学”为组织起点：先接触具体对象和问题，再引入真正需要的抽象结构；条目按课程与章节组织，而不是照搬实现库的模块划分。它在 Mathlib 的基础上增加动机、直觉、证明思路和语言对照。成熟接口可以直接复用，但须解释为什么它就是教材里的概念。

一个完整知识点有三层：**Lean 层**明确说了什么并给出证明；**叙述层**解释为什么、怎么想、哪里容易误读；**索引层**帮助找到来源与前置知识。叙述层不是代码注释的扩写，它承担“形式化表达是否忠实”的解释责任。Entry 文档依次展开动机、定义与承载、自然语言陈述、Lean 对照、思维脉络、对应映射、依赖、应用与边界。

## 已有文档分别回答什么问题

| 面向人类的文档 | 读者可以从中得到什么 |
|:---|:---|

截至本次阅读，库中登记 565 个已验证知识条目、694 条直接教材依赖和 73 项出版来源。条目数量说明资产规模，不代表所有课程或论文已经完成。当前课程状态以 ROADMAP 为准；本文没有重新执行整库验收。

# 2　著名定理只有名字：怎样建立可审核的接口？

**项目不假设一个著名名字对应唯一的数学接口，也不宣称替整个数学共同体制定标准。** 名称用来发现定理家族；真正可调用、可验收的是有来源和明确条件的具体声明。项目的约定来自公开契约、数学审核和使用者，不能由 Agent 的投票或名字相同来代替。

![定理名称到明确接口。C1、C2、C3 是图内契约编号；关系目录是建议扩展，三个 Hahn–Banach 声明已存在于源码。](theorem-contract.pdf){width=100%}

**具体契约固定六项：** 来源与原文位置；对象及数域；量词和所有显隐式前提；结论及相等方式；退化情形与适用边界；Lean 具名声明及其正式承载。同名但前提不同的版本保留为不同声明；Entry 是知识组织单元，当前一个 Entry 可以关联多个声明，不能仅凭 Entry 标题调用定理。[S2、S6]

## 仓库已有实践：Hahn–Banach 并非一个模糊接口

`functional-analysis.hahn-banach.extension` 同时解释三条具名声明：[S12]

| 具体形式 | 正式前提和结论 | 已有证明关系 |
|:---|:---|:---|
| 实代数支配延拓 | 实模、子空间线性泛函、正齐次与次可加控制函数；延拓保持支配 | 调用 Mathlib 支配延拓接口 |
| 实等范数连续延拓 | 实半赋范空间、连续线性泛函；延拓保持算子范数 | 调用 Mathlib 等范数接口 |
| 实不增范数连续延拓 | 同上一行；延拓范数不大于原范数 | 源码从等范数声明直接推出 |

本条不声称复数推广、延拓唯一或一般向量值延拓；源码也没有把上述两层证明成任意条件下可互换。教材中联系两层的思路说明，与已经具名证明的桥应分别记录。

## 从局部约定到可演化的定理家族

建议建立版本关系目录：**对象转换下的等价、增加条件后的特化、推广、推论、不等价反例、待澄清**。每条关系注明条件和具名证据；仅有两个可证命题的 `P ↔ Q` 不能证明语义忠实，因为两个真命题本就等价。应核对对象映射、假设和结论各自的含义。

出现审阅分歧时，先回到原文上下文；无法消除则保留两个版本及分歧记录，阻塞有争议的对应声明。可为课程选一个公开的默认接口，其他版本继续可检索，迁移需桥与下游复验。这承接 DESIGN 的多版本共存理念：调用量提示复用价值，不能裁定语义正确性。当前尚无完整自动关系目录。[S6、S13]

# 3　真实案例：如何核对 ε–N 收敛定义

仓库中的 `analysis.sequence.definition` 提供一个完整且易检查的例子。正式源码为 `SandronesLibrary/Analysis/Sequence.lean`，教材文档为 `docs/entries/analysis/sequence/definition.md`。[S7]

**教材意思：** 对实数列 $u$ 与实数 $l$，无论给出多小的正误差 $\varepsilon$，都能找到自然数起点 $N$，使此后每一项与 $l$ 的距离小于 $\varepsilon$。

```lean
def SequenceConvergesTo (u : ℕ → ℝ) (l : ℝ) : Prop :=
  ∀ ε > 0, ∃ N : ℕ, ∀ n ≥ N, |u n - l| < ε
```

| 教材中的片段 | Lean 中的对应 | 要排除的错误 |
|:---|:---|:---|
| 实数列、实数极限 | `u : ℕ → ℝ`、`l : ℝ` | 把对象层级或数域换掉 |
| 任意正误差 | `∀ ε > 0` | 漏掉正性，或只检查某一个误差 |
| 存在起点 | `∃ N : ℕ` | 把存在换成固定常数 |
| 此后全部项 | `∀ n ≥ N` | 只检查一个项或一段有限样本 |
| 距离严格小于误差 | `|u n - l| < ε` | 把绝对值或不等号方向写错 |

这里最关键的是 **$N$ 可以依赖于 $\varepsilon$，不能依赖于随后选择的 $n$**。若误写成 $\exists N,\forall\varepsilon>0,\forall n\ge N$，则尾部每项与 $l$ 的距离必须小于所有正数，在实数中意味着尾部恒等于 $l$；这比通常的收敛强得多。编译器可以检查错误版本的证明，却不会提醒作者“你换了教材概念”。

## 从定义到桥，再到实际使用者

源码先给出 `sequenceConvergesTo_iff_epsilon_N`，以定义展开保证公式与谓词一致；再用 `Metric.tendsto_atTop` 和 `Real.dist_eq` 证明：

```lean
theorem sequenceConvergesTo_iff_tendsto {u : ℕ → ℝ} {l : ℝ} :
    SequenceConvergesTo u l ↔ Tendsto u atTop (𝓝 l)
```

最后，`sequenceConvergesTo_unique` 真正接受两个教材收敛假设，经过桥转换后使用滤子极限唯一性，得到两个极限相等。这形成可审核的链：**教材定义 → 公开展开 → Mathlib 等价桥 → 上层公开定理**。桥在 Lean 中证明两个正式表达等价；教材文字与第一个公式之间的对应由上表和独立审阅确认。

读者不必先熟悉滤子体系，也能用教材定义理解并调用极限唯一性。需要深入时，再沿公开桥检查 Mathlib 承载。这正是 DESIGN 的“用到再引入”：抽象结构服务于已有数学意思，每一层都有可回看的解释。本次对这些正式接口的定向检查已通过，详细复验记录放在附件。

# 4　人类如何读 Lean：把 tactic 还原成数学动作

本库的 `LEAN-TACTIC-REVIEW-GUIDE.md` 面向“会数学，但不一定会写 Lean”的审阅者。读一段证明时，先问：**现在要证什么？已经知道什么？这一行产生了哪些新义务？** `⊢` 后是目标，上面是对象与假设。读懂这个状态，比记住几十个 tactic 名称更重要。[S14]

| 证明脚本中的动作 | 纸面数学中的意思 | 人类审阅重点 |
|:---|:---|:---|
| `intro` | 固定任意对象，或引入前提 | 对象是否仍任意，假设是否来自原文 |
| `apply` | 用一个定理，将结论化为它的前提 | 调用了哪个版本，新增条件是否满足 |
| `refine` | 先给构造或见证，再证明它满足条件 | 构造是否正确，剩余义务是否全部完成 |
| `constructor` | 证明合取的两部分，或等价的两方向 | 是否遗漏分支或只证明了单向 |
| `rcases`／`obtain` | 从存在性结论中取对象并拆出性质 | 所取对象与后续使用是否一致 |
| `rw`／`calc` | 定向改写，或逐行连接纸面推导 | 等式与不等式方向、条件是否正确 |

## 一个真实的两行证明

Hahn–Banach 的“不增范数”版本直接使用等范数延拓：[S12]

```lean
obtain ⟨g, hg, hnorm⟩ := hahnBanach_exists_extension_norm_eq S f
exact ⟨g, hg, hnorm.le⟩
```

第一行取得延拓 `g`、它在子空间上等于 `f` 的证据 `hg`，以及范数相等的证据 `hnorm`。第二行交回同一个 `g`，保留延拓性质，并将“范数相等”变为“范数不大于”。数学内容就是：**等范数延拓当然也是不增范数延拓**。审阅者应去看所调用的等范数定理，而非因为代码很短就认为整条延拓理论简单。

## 自动化不应遮住关键数学

指南区分结构步骤和末端计算：`ring` 整理交换环多项式，`linarith` 组合线性不等式，`norm_num` 验证具体数值；它们不会自己发明收敛论证或解释原文。`simp` 可能调用已经登记的化简定理，审核关键步骤时应查清用了哪些规则。`rfl` 表示按定义计算后相同，遇到“深刻结论一行完成”时应回看定义是否已藏入目标。

`LEAN-TACTIC-STATE-ATLAS.md` 是配套实例册，以正式源码中的例子展示执行前后状态，并标出尚无实例的覆盖缺口；其中状态依源码复原，具体争议仍以编辑器与编译器现场显示为准。`?_` 是待后续完成的子目标，`_` 是让 Lean 推断参数；两者与绕过证明的 `sorry` 不同。

审核报告因此应写“把极限唯一性转为滤子接口，再使用已验收的唯一性结论”，而非仅写“用了 `exact`”。人类保留对含义、范围与证明路线的判断，Lean 负责检查正式推理。

# 5　从 Playbook 到论文形式化：先看清证明，再并行

Playbook 的核心方法是**先把完整定理搭成可组装的框架，再逐个完成证明责任**。研究者先固定定义与下层引理的接口，让上层确实能调用它们；每个未完成步骤都是明确任务。临时草稿中的 `sorry` 只表示待办，正式库必须全部消除。若反复尝试五次仍失败，应重新拆解，而非继续猜 tactic。[S3]

![论文形式化工作流。语义对应 A 与形式证明 B 分别验收，两者通过后才检查冻结范围的覆盖 C；虚线表示返工。](workflow.pdf){width=100%}

## 编译通过以外，还要过两道门

**A：有没有表达原文？** 定位原文与上下文，核对对象、量词、假设、结论和边界。非作者审阅者先独立回译 Lean 陈述，再与原文比较。明确新增的假设只能形成受限结果，不能悄悄当作原文前提。

**B：有没有真正证明？** Lean 检查正式命题及其证明；依赖的结果与公理需披露。还要避免把待证结论直接加入前提，或把它藏在定义字段里。编译器可以接受“已知 P，所以 P”，这并未证明原论文的 P。[E1–E3]

**C：有没有完成所承诺的范围？** 逐项列出定义、引理、主定理和必要步骤；未覆盖部分继续保留。不能靠删除困难步骤，把完成比例改成 100%。复用现成最终定理可以完成结果形式化，却不自动等于重建原论文证明。

小组分工沿数学依赖展开：定义负责人先固定承载与桥；证明者并行完成独立引理；审阅者检查语义与边界；学科负责人把全部步骤组装并亲自验收；Main 负责共享知识状态与最终集成。一个难点解决后，其数学条件、有效方法和误用边界应沉淀进可检索经验，而不是随聊天窗口消失。

这把 Playbook 的“自我驯化”落实为持续积累：**遇到困难 → 查真实用法与目标状态 → 按数学含义拆解 → 编译复验 → 记录可复用经验**。多 Agent 的优势来自责任清楚和共享接口；同一模型的多份赞同意见可能重复同一误解。

# 6　ROADMAP：从课程地基走向论文，而不是追逐名词

ROADMAP 将库的扩展写成课程路径、具体批次和依赖门。它要求先建立能解释、能使用的课程基础，再让论文结论“下沉”到这些基础之上。某个著名 theorem 已在 Mathlib 存在，不意味着本库已经掌握其对象、条件和证明链。[S5]

## 人类学习路径如何影响建设顺序

| 路线 | 建设思路与后续用途 |
|:---|:---|
| 分析与线性代数 | 从实数、数列、极限到微积分；从线性映射到谱与 SVD |
| 抽象代数与拓扑 | 建立结构、商对象与空间语言，供后续理论复用 |
| 实分析与泛函分析 | 测度积分支撑概率；无限维空间、算子与对偶支撑分析 |
| 概率与统计 | 先有概率模型、收敛与条件结构，再谈推断与最优检验 |
| 高阶学科 | 流形、PDE、代数几何等逐项受各自课程前驱约束 |

这是路线关系的概述，并非这些课程均已完成。例如当前线性代数 L1–L7 已进入 Main，泛函分析 F1–F5 已完成而后续仍在推进；高阶学科大部分仍受依赖门限制。具体状态必须回到 ROADMAP 总览与相应章节。

路线图还强调两项人类可理解的验收：阶段末能力必须被下一阶段实际使用，才算能干活；例子与反例应随理论建设持续巡视，不能等整库结束后补齐。综合书稿《水仙十字的世界式》则消费已验收条目，将单个知识点连接为跨学科叙事，不另造一套进度。[S8]

## “验证一篇论文”应先讲清要验证哪一部分

**结果形式化**证明选定数学结论，可采用现代证明或准确披露的已有结果。**原论证重建**进一步对应原文关键推理步骤。**算法实现验证**还需要程序、数值误差或成本模型；它不能由实数上的数学定理自动保证。原文实验、历史判断和物理解释也须另行验证。

每批建议围绕 3–6 个互相支撑的公开声明，说明原文目标、采用的证明路线、新增基础和未覆盖部分。论文候选分为“基础已满足，可建首批方案”“可调查但基础仍有缺口”“远期依赖尚未满足”。Eckart–Young 与 Banach–Steinhaus 属于前一类；Nikodym 与 Wedderburn 仍需桥接研究；Green–Tao、Cohen 等列在长期路线。[S5]

论文形式化首先形成一份读者能理解的承诺，例如：“完成有限维实矩阵的最佳低秩逼近结果，采用现代证明；未重建原论文全部推理，未涉及浮点实现。”最后按同一承诺报告主定理、关键责任与遗漏，使成果可持续被调用。

# 7　数百 Agent：分层审核，把 Main 变成发布与治理层

当前“子 Agent → 学科负责人 → Main”适合有限并行；若几百个交付都需 Main 手工整理 Registry、逐份重审和解冲突，输出越快，积压越大。扩展方向是**分散数学验收、自动汇总共享状态、按批发布**。下图是未来架构，实施前需通过 RFC 调整职责规程。

![建议的规模扩展架构。以 300 个证明 worker 为例；负责人、审阅者和 CI 资源另计。实线为产物提交，虚线为契约、调度与返工反馈。](scale-architecture.pdf){width=100%}

**小组层：** 每组负责人直接管理 2–3 个互不重叠的证明 worker，另有非作者语义审核与验证执行器；保持现有亲自验收责任。输出具备接口、依赖、公理、复验记录的已提交批次。公共定义由唯一接口负责人维护。

**学科集成层：** 多个小组进入同一学科候选分支，由具备专业判断能力的维护者验收联合导入、实例影响和教材边界。跨小组冲突在此解决；跨学科接口先提交契约 RFC。学科包携带结构化 Entry／文献更新建议，不直接改 Main 共享文件。

**发布层：** 控制器核对包的契约、签名、所有权和证据；唯一发布写者合成 Registry、imports 与派生文件，在最新候选提交上执行验收队列，失败批次拆分定位。Main 审核跨学科 API、额外公理、例外与最终发布；稳定接口内的常规批次由学科验收负责，保留抽查和追溯。

示例划分为 100 个小组，每组 3 个证明 worker，归入 10 条学科集成队列。这是容量设计示意，未测量吞吐。Main 收到的是可机器检查的学科包与异常清单，其成本取决于接口变化和发布频率。更长期可采用固定 Lake 依赖版本的分库，根库只接收已验收版本；Mathlib 社区也建议独立项目使用依赖仓库。[E5]

# 8　集成怎样不压垮 Main：五项具体工程安排

增加层级不能凭空减少工作。规模扩展必须把常规问题交给有权限、有能力的层级解决，把机械整理交给程序，同时保留数学判断的责任。以下是建议实施的机制，不是当前仓库已经运行的系统。

## 1．先约定共享接口，再增加证明者

定义、关键桥与高扇出接口由专门负责人统一维护。每个任务拿到明确命题、允许的假设和上游版本；独立分支只写自己的文件。公共接口改变就通知受影响的下游重新检查。依赖图要覆盖实际调用、导入和实例影响；没有文本冲突也可能发生数学或组合冲突。

## 2．用“学科验收包”代替大量散件

小组负责人逐项验收，学科维护者处理联合导入和学科内冲突。交给发布层的是完整批次：证明、教材解释、依赖、公理、语义审核和更新建议都已齐备。Main 无须重新从聊天中寻找证明、补列条目或猜测谁审过。数学发现与纯排版问题分开处理，出版整理可以由文档流水线承担。

## 3．按候选批次合并，而非相信旧构建

发布程序将验收包叠加到最新目标分支，统一生成共享索引，再检查这个实际候选整体。目标基线变化就重新排队；只有候选本身通过，才由唯一发布写者推进最终版本。GitHub 的合并队列提供了类似的候选组检查思路。[E6] 常规更新按周期或容量合批，完整构建放在发布门；失败拆分定位，受影响批次返工。公开定义迁移单独安排，不混在普通证明批次中。

## 4．控制在制品，让审核跟得上

为每个小组、学科和发布队列设待审核任务上限。当语义审核已经积压，应停止派发新证明，优先解决复验和返工。系统实际速度受最慢环节限制：证明者再多，也无法弥补缺少数学审阅者。观察首次通过率、返工、等待时间、专家审核时间、构建成本和论文覆盖，而不是只统计 Agent 产出。

## 5．任务和经验可恢复，不依赖窗口常驻

中心控制器保存待办、负责人、依赖与审核结果；领取任务时确认唯一写者。Worker 失联须先阻止旧进程继续写，再重新派工；构建与临时探测隔离。接班者依据已提交成果和书面交接继续工作。经验进入 Playbook，已解决知识进入 Entry，人工争议进入 review，论文总体进度进入范围清单。

可先从 10、30、100 个证明 worker 分级演练，确认审核队列、跨模块组合和失败恢复稳定，再考虑 300。Main 的压力应从“每个证明都手工整理”转为“治理接口、处理异常和批准发布”。它仍须具备足够的发布与抽查能力；大型规模的收益在实际测量前不能宣称。

# 9　论文案例：Eckart–Young 低秩逼近怎样拆成任务

路线图已把 Eckart–Young（1936）的低秩逼近论文列为 `paper_ready` 候选，首批范围为有限维矩阵的截断 SVD、误差公式与最佳秩 $k$ 逼近。出版者页面确认论文书目信息和最小二乘矩阵逼近主题。[S5、E4]

**本页是实施设计，不是论文验证完成报告。** 本次核验了书目信息、路线图与本库 SVD 源码，没有逐页读取原论文全文。以下使用现代数学表述说明任务拆解；原文页码、编号、原证明结构及每项对应关系，必须在实际立项时补齐并审核。首批建议限定实矩阵；复数推广单独登记，避免冒充原文范围。

## 冻结一个准确的主结论

取 $A\in\mathbb R^{m\times n}$，$d=\min(m,n)$，$0\le k\le d$。将奇异值按 $\sigma_0\ge\cdots\ge\sigma_{d-1}\ge0$ 排列，由同一份 SVD 证书构造截断矩阵 $A_k$。明确使用

$$
\|A\|_F^2=\sum_{i=0}^{m-1}\sum_{j=0}^{n-1}|A_{ij}|^2.
$$

目标是证明 $\operatorname{rank}(A_k)\le k$，以及对每个同尺寸、$\operatorname{rank}(B)\le k$ 的矩阵 $B$，

$$
\|A-A_k\|_F^2=\sum_{i=k}^{d-1}\sigma_i^2
\quad\text{且}\quad
\|A-A_k\|_F^2\le\|A-B\|_F^2.
$$

此表述要求最佳性相对于**全部**秩受限候选，而不是有限样本；没有声称最佳矩阵总是唯一，也没有声称任意酉不变范数的推广。项目现有 `operatorNorm` 是诱导算子范数，不能把它静默当作 Frobenius 范数。[S11]

| 任务 | 交付与前置依赖 | 责任分工 |
|:---|:---|:---|
| D　承载与定义 | 矩阵—线性映射桥、Frobenius 平方、截断定义；复用现有 SVD 证书 | 定义 Agent，负责人先验收 |
| L1　截断秩界 | 从截断表示证明 `rank ≤ k`；依赖 D | 证明 Agent A |
| L2　误差公式 | 正交展开、范数关系与尾和；依赖 D | 证明 Agent B |
| L3　任意候选下界 | 对任意秩受限 B 建立误差下界；先冻结独立契约 | 后续独立证明任务 |
| T　最佳逼近组装 | L1、L2、L3 → 主结论及非空候选实例 | 负责人联合导入验收 |

现有 `MatrixSVD.lean` 已有分解证书、矩阵分解和奇异值—秩接口，是可用基础；本次目标源码搜索没有找到项目自有的 Frobenius 最佳低秩逼近声明。因此 SVD 入库与这篇论文核心结论入库应分别报告。L3 的下界是独立证明责任，不能只完成截断构造和误差公式就宣称最佳性。

Examples 另验 $k=0$、$k=d$、零矩阵、矩形矩阵和重复奇异值。$A=\operatorname{diag}(1,1)$、$k=1$ 时，保留任一坐标都给出相同误差，可用于揭示“总是唯一”的误读；一般唯一性条件不进入本批承诺。

# 10　发展构想：可理解的接口、可积累的方法、可扩展的协作

本项目的长期目标，是让新问题的形式化建立在已理解的知识之上。已有 Entry、证明指南、Playbook 和课程路线使这个目标具有实际基础；下一步应把定理版本关系、论文范围和分层审核连接起来。

## 三个值得先做的示范

**同名定理的接口示范。** 选一个有多个常见版本的定理，展示它们的来源、假设、结论、真正可证明的关系与不可互换边界。让数学审阅者可以指出“我认可的是哪一版”，让证明者知道“下一步调用哪一条”。默认接口是项目公开约定，其他版本继续保留。

**一篇论文的闭环示范。** 选择基础已解锁的候选，先冻结一小组结论，再完成语义审核、证明组装、例子挑战和范围报告。已登记的 SVD 不等于 Eckart–Young 已验证；调用现成定理也不等于复原整篇历史论文。一次诚实而完整的小范围交付，比一个没有界定范围的“全文完成”更能支撑后续建设。

**多层协作的容量示范。** 先以几个小组验证学科验收包与自动候选队列；证明、语义审核和发布能力一起扩容。再按阶梯增加并发，记录等待、返工与最终覆盖。数百 Agent 的架构是未来方案，尚无本项目吞吐测量。

## 本次考察能支持什么判断

结构审计通过，ε–N 案例的定向构建和接口探测通过；Hahn–Banach 的多形式接口直接来自现有源码。结构审计能检查登记与依赖的一部分一致性，不能自动判定自然语言含义。本文没有重新验收全库，没有启动论文证明，也没有修订既有数学条目。细节、命令和日志见配套复现附件。

DESIGN 中多版本共存与人类思维脉络的理念值得延续；其中早期状态设计、自动化设想与现行执行规程需分别阅读。调用量可以提示某版本更常用，不能判断它在数学上正确或适合当前原文。Lean 保证正式证明，人类审核保证解释责任，ROADMAP 保证建设顺序。
