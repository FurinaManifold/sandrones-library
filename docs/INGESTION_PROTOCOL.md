# Sandrone's Library — 纳入协议（Ingestion Protocol）

> **本文件是整个库"可扩展性"的契约。**
> 目标：给一个数学能力合格的模型（2026 标准），输入一篇文章/书中的某个结论，
> 它能**按固定流程**把这个结论以「Lean + 自然语言」双语形式纳入 Sandrone's Library，
> 并且每一步的产物、验收标准都明确、可审计、可部分并行。

---

## 0. 参与者

- **纳客（Ingestor）**：LLM（人可监督或纯自动化），负责产出叙述层与形式化层。
- **校验者（Verifier）**：Lean 内核（机器，唯一裁决正确性的实体）。
- **审计者（Auditor）**：脚本 + 人。检查协议是否被遵守、元数据是否一致。

三者权力分离：**正确性只由 Lean 裁决**，纳客不得自评"证明好了"；
**完整性只由审计者裁决**，纳客不得声称"依赖已满足"而不提供清单。

---

## 1. 输入 / 输出

**输入**：一篇论文或一本书 + 指定其中的结论（可含：节号、定理编号、陈述、上下文、作者草稿）。

**输出**（三者缺一不可，且互相对应）：

| 产物 | 路径 | 状态 |
|---|---|---|
| 叙述层 | `docs/entries/<entry-id>.md` | 由纳客写 |
| 形式化层 | `SandronesLibrary/<域>/<文件>.lean` | 由纳客写，Lean 校验 |
| 元数据 | `index/registry.json`（该条目的记录） | 由脚本/审计者更新 |

---

## 2. 五步流程

### Step 1 — 分解（Decompose）

把目标结论拆成一颗**推导树**：

```
目标结论 C
 ├─ 定义 D1（若 C 涉及新概念）
 ├─ 引理 L1 → C          （局部论证）
 ├─ 引理 L2 → L1
 └─ 前置事实 P1, P2      （已在库中 / 来自 mathlib / 需要一并纳入）
```

要求：
- 树的每个节点要么是**库中已有条目**，要么本次一并纳入，要么来自 mathlib（标注引用）。
- 分解产物写入 `entry.md` 的「依赖」节，逐条列出并注明来源类别。

**验收**：审计者核对依赖清单 —— 每个依赖项都能指出它在库中的 id、mathlib 中的名字、或本次新增的占位条目。

### Step 2 — 双语转写（Transcribe）

产出两个半成品：

1. **人类证明草稿**（自然语言，写进 `entry.md` 的「思维脉络」节）：
   - 像 R1 一样把推理链写全，但**清洗过**：去掉胡言、保留失败路径的"为何此路不通"。
   - 明确写出每一步使用的直觉与依赖。
2. **形式化陈述草稿**（写进 `.lean` 文件）：
   - 定义 / 定理陈述（先写陈述，不写证明）。
   - 每个符号旁边标注「自然语言 ↔ Lean 映射」注释，供对齐。

**验收**：陈述草稿中的每一个"已入库依赖"都能在 Lean 中 `#check` 出对应项。

### Step 3 — 形式化（Formalize）【本协议的心脏】

迭代闭环，模型 + Lean 协作：

```
  证明草稿（人话） → 写成 Lean 策略脚本 → lake build 编译
      ↑                                      │
      └── 读报错，修陈述或修证明 ←—— 有错 ←──┘
                                    │ 无错
                                    ▼
                             形式化层完成
```

- 允许使用 `by omega / linarith / aesop / ring_nf` 等自动化策略，
  但**关键推理步骤必须手写并注释**（证明的"脑回路"留在注释里）。
- 允许 `sorry`，但**仅限** `pending` 状态，且必须在文件头集中登记
  （`#exit` 之后的临时草稿区），不得混入正式区域。

**自我驯化规则（强制，针对"编译-修复"闭环的低效循环）**：

1. 修复报错时，**禁止盲目试错**（改个姿势再编译一次）。
2. 按 [LEAN-PLAYBOOK.md](LEAN-PLAYBOOK.md) §0 的顺序：先把报错翻译成自然语言
   （"期望类型 vs 实际类型" = "我要的东西与手头的东西对不上"）→ 查 Playbook 的
   "数学意图 ↔ tactic 映射"（§2）→ 用 grep / `#check` 去 mathlib 源码找现成证明，
   **观察该 tactic 使用前、后的目标状态**，用语义理解，再写。
3. 新教训**必须**按 §3 格式登记回 Playbook（症状/诊断/解法/出处），否则本步不视为完成。
   —— 这是 self-harness 闭环：形式化技能随库增长，而不是每个会话从零开始。

**验收**：`lake build` 通过；文件中无 `sorry`；关键步骤有思路注释。

### Step 4 — 校验（Verify）

脚本 + 人工双检：

| 检查 | 工具 | 通过条件 |
|---|---|---|
| 机器校验 | `lake build` | 零错误零警告（lint 也过） |
| 陈述一致性 | `scripts/audit.py` | 陈述文本与 `entry.md` 的「陈述」节一致（占位符、记号同步） |
| 依赖完整性 | `scripts/audit.py` | 形式化层实际使用的 mathlib 定理 ⊆ 声明依赖 ∪ mathlib |
| 来源引用 | `scripts/audit.py` | `provenance` 字段可定位（文章/书/节号/结论编号） |
| 无隐藏假设 | 人工抽查 | 证明未在 `premises` 之外使用未声明的非 mathlib 事实 |

### Step 5 — 注册（Register）

1. 状态置 `verified`，写入 `index/registry.json`。
2. 更新依赖图（为每个依赖条目的 `dependedOnBy` 追加本条目）。
3. 若本条目**新增了命名空间或高频短语**，同步更新 `docs/mapping/`。
4. 提交（git），commit message 含 entry-id。

**验收**：`audit.py --all` 通过；依赖图无环、无悬空引用。

## 3. 防失真铁律（违反即打回）

1. **不得**把论文没写的参数补成事实 —— 缺口写 `unresolved`。
2. **不得**用流畅叙述掩盖未完成的证明 —— 未验证写 `pending`。
3. **不得**在 `verified` 条目中静默引入 `sorry`。
4. **不得**把"LLM 觉得对"当"Lean 证明过了"。以编译结果为准。
5. 叙述层的每一条断言可追溯：标 `source`（来自文章/推理/库内）。

## 4. 为什么 2026 年的模型能走通 Step 3（对比 2024）

- 2024：模型给出"看起来对的证明"，没有工具能自动验证 → 无法收敛。
- 2026：Lean 即工具。模型写一个版本 → 编译器返回**精确的**错误位置与期望类型 →
  模型据此修改 → 收敛到可编译证明。**编译器是闭环的裁判**，不需要模型自证正确。
- 本协议的全部价值就是把"LLM 有能力迭代修证明"这个 2026 年事实
  组织成"知识能增量累积"的系统。

## 5. 纳入能力评测（扩展性的量化）

定期（如每季度）从教材/论文抽样结论，跑本协议，记录：

- **纳入通过率**：随机结论中达成 `verified` 的比例。
- **平均迭代轮数**：Step 3 的编译-修复次数（衡量转写质量）。
- **依赖复用率**：目标结论的依赖中，已存在于库中的比例（衡量库的覆盖面）。
- **单条目耗时 / 算力成本**。

这些指标构成"数学大厦能不能长大、长多快"的体检报告，写入 `index/metrics.json`。

**版本调用量指标**（多版本价值的客观度量，由注册脚本自动统计）：

- `family` 级别的 `dependedOnBy` 总量 = 该数学结论在库中的价值。
- `variant` 级别的 `dependedOnBy` 数量 = 哪个版本（教材/形式化）最常被调用。
- 定期看这两个数字，就能知道哪些教材版本值得继续扩充、哪些版本被边缘化。
  **这不是人的偏好，是库内实际使用频率的投票。**

### 6.1 多版本纳入规则

- 纳入一个"人话版本"时：若该 family 尚无 `verified` 条目 → 先建主条目（`variant: generated` 或某教材）；
  若有 → 直接追加新变体条目（`<family>.<variant>`），不必改动旧条目。
- 新版本只需承诺"与 family 的数学结论一致"，不必与旧版本陈述逐字相同。
- 引用方写 family id 或具体变体 id 都合法；解析规则见 SCHEMA.md。

## 6. 并行与协作

- 同一推导树中**无依赖关系**的子树可以并行纳入（不同分支由不同会话完成）。
- 叙述层与形式化层可并行初稿，但**注册前必须合并对齐**（Step 4 的陈述一致性检查）。
- 一个条目被标记 `verified` 后，即可被其他纳客当作前置依赖使用。
