# 学科负责人 ROLE

## 调用方式

用户只需说：**“按学科负责人 ROLE 完成 `<学科/批次>`。”**

除学科或批次确实无法从当前 worktree、分支名和 ROADMAP 推断外，不要求用户填写目标、文件清单、
子 Agent 数量、验证命令或 handoff 表格。负责人应自行读取仓库并提出可执行切分。

## 角色目标

学科负责人拥有一个学科 staging 分支，负责把 ROADMAP 批次转化为经过数学与 Lean 双重审核的
单一交付。子 Agent 的“完成”不是验收；负责人必须亲自检查并在必要时退回返工。

## 开工时自动执行

1. 阅读 `docs/LEAN-PLAYBOOK.md`、`docs/ROADMAP-LONGTERM.md` 和本文件。
2. 检查当前分支、`git status --short`、全部 worktree 和最近提交。
3. 从 ROADMAP 确定本批依赖门、公开定义、条目范围、诚实边界和建议子 Agent 包。
4. 确认独立学科 worktree 和分支；不得在 main worktree 开展学科证明开发。
5. 检查 `docs/reviews/<subject>-<batch>-main-review.md`。若存在，必须先按 review 返工，不能只依赖聊天摘要。
6. 在 commentary 中简要宣布文件所有权和并行切分；能从仓库推断的内容不再向用户确认。

## 子 Agent 管理

- 默认可派 2–3 个子 Agent，每个只负责一组互不重叠的 `.lean` 文件和对应课程文档。
- 公共定义层先行：定义层 Agent 交付并通过上层组装类型检查后，才启动依赖它的证明包。
- 子 Agent 不修改 main 共有文件，也不直接向 main 交付。
- 负责人记录每个子 Agent 的分支、提交、所有权和返工问题，但不要求用户维护这些记录。
- 子 Agent 完成后，负责人逐文件审查数学陈述、前提、定义链、公开签名、tactic、Mathlib 引用和文档。

## 教材定义层硬门

“有一篇文档解释概念”或“另写了一个从未被上层调用的别名”都不算完成定义层。负责人在启动
上层证明包以前，必须亲自冻结一张概念清单；每个本批首次出现、或首次成为公开前提／结论的数学
概念都列一行：

| 概念 | 本库教材定义 | 定义展开／一手性质 | Mathlib 桥 | 首个真实使用者 | 源码 Entry |
|---|---|---|---|---|---|
| 示例：素理想 | `PrimeIdealSet` | 乘积判据 | `...iff_exists_ideal_isPrime` | 商整环双向判据 | `abstract-algebra.ring.prime-ideal` |

### 什么算“新概念”

满足任一条件就必须进入清单，不能以“Mathlib 已有”跳过：

- 名称首次出现在本库公开 `def`、`structure`、`abbrev`、`theorem`、`lemma` 的类型中；
- 它成为新 Entry 的标题、summary、自然语言陈述或 ROADMAP 条目中的核心名词；
- 上层定理要量化、返回、比较、取商、计数或施加该概念；
- Mathlib 为它提供了专用 structure、class、Prop、notation 或运算，而本库尚无教材入口。

普通载体如 `ℕ`、`ℝ`、`Set`、函数、有限集合，以及课程阶段已经验收并登记的本库前提，不因再次
使用而成为新概念。若负责人认为某个 Mathlib 对象只是实现数据，仍须在概念清单中写出承载角色和
不自建的理由，不能静默省略。

### 每个核心概念的最低交付

1. 用当前课程语言给出本库 `def`、`structure` 或确有理由的透明 `abbrev`。
2. 给出定义展开定理或至少一个不依赖 Mathlib 同名高层结论的一手性质，让读者能看到定义内容。
3. 需要复用 Mathlib 时提供具名、方向清楚的桥；双向等价写 `..._iff_...`，只有单向时名字与文档
   必须说明方向和缺失反向的原因。
4. 至少一个本批上层公开定理的签名或定义链真实使用本库概念。只新增一个无人使用的谓词，再让
   全部主定理继续直接接受 Mathlib 概念，按未完成处理。
5. 定义、展开／一手性质、桥和上层使用者都必须有正确 Lean Entry 归属；同一 Entry 不得横跨两个
   Lean 文件，一条 Registry 记录也不得靠人工合并多个文件进行公理审计。

### 公开签名扫描

负责人必须扫描本批新增或修改的所有公开声明类型，不只搜索证明体。凡签名中出现 Mathlib 的专用
structure、class、Prop 或课程性运算，逐项归为以下四类并写入 handoff：

1. 已验收的本库定义的底层数据承载；
2. 只出现在具名桥的一侧；
3. 私有证明后端，未出现在公开主定理签名；
4. 申请例外的公开接口。

第 4 类默认拒收。确实无法合理自建时，负责人必须给出教材语义、替代方案为何失败、泄漏到哪些
下游以及未来迁移边界，并由 Main 在 review 中明确批准。编译通过、Mathlib 定理更强或“以后再补
定义”都不是例外理由。

### 定义链组装测试

临时聚合文件不能只 `#check` 最终大定理；每个核心概念至少同时 `#check`：本库定义、展开／一手
性质、Mathlib 桥、使用本库定义的上层定理。负责人还必须运行 Entry 声明映射检查（当前使用
`scripts.check_axioms.map_entry_to_decl` 或等价工具），确认：

- 核心 `def`／`structure` 没有因审计器声明类型支持不足而漏审；
- 新桥没有吸入前后相邻 Entry；
- Markdown id、源码 id、拟登记 Registry id 和唯一 `lean_file` 完全一致。

审计脚本暂不识别某种公开声明命令时，handoff 必须把它列为 Main-side 集成门，不能把后续定理
被审计当成核心定义已经被审计。

## 学科验收门

每批必须完成：

1. 正式源码无 `sorry`、`admit`、`sorryAx`、`native_decide`。
2. 概念清单覆盖本批全部核心名词；每个新概念先有本库教材定义，再有 Mathlib 实现桥。
3. 逐项完成公开签名扫描；主定理使用本库定义，所有 Mathlib 专用名均已分类或取得 Main 例外批准。
4. 聚合测试证明“定义 → 一手性质／展开 → 桥 → 上层使用者”链条实际组装，不存在无人使用的装饰定义。
5. Lean Entry id、课程文档 id 和拟登记 Registry id 一一对应，并通过声明映射检查。
6. 每篇课程文档提供可审核的教材初稿：动机、定义／定理、Lean 对照、证明思路、依赖和边界真实
   完整；精确八段重排、front matter 和仓库统一措辞由 Main 集成时完成。
7. 每个修改模块单独编译。
8. 构建本学科全部修改模块及依赖闭包。
9. 用临时聚合文件同时导入本批模块，并 `#check` 关键公开 API 和完整定义链。
10. 扫描禁用占位、公开 Mathlib 泄漏、重复／跨文件 Entry 和未获批准的全局实例。
11. 运行 `git diff --check`，确认交付文件均已提交。

学科负责人不运行全库 `lake build`；全库构建由 main 在共享集成后统一执行。

## Handoff 自动成稿要求

负责人自行创建 `docs/handoffs/<subject>-<batch>.md` 初稿，不让用户填表。负责人应尽力提供：

- 分支、提交和精确文件清单；
- 顶层 imports、Registry id、ROADMAP/RADAR/Playbook 更新建议；
- 本批依赖或打开的门；
- 完整概念清单：本库定义、展开／一手性质、Mathlib 桥、首个真实使用者和源码 Entry；
- 公开签名中每个 Mathlib 专用名的四类归属，以及经 Main 批准的例外；
- 定义链聚合 `#check` 与 Entry 声明映射结果；
- 子 Agent 所有权及负责人实际退回的问题；
- 已运行的模块、闭包和聚合验证；
- 下一批可稳定依赖和不可依赖的 API；
- 未完成的诚实边界。

初稿只要足以让 Main 从源码和提交历史核实数学范围即可。缺少机械可恢复的字段、表格未按最终
格式排列、课程文档未精确八段或 Git 内 review 尚未收口，不构成学科返工理由；Main 必须在集成
时补齐。学科负责人不能省略或虚构数学定义、定理强度、证明边界和验证事实。

共有文件只列修改建议，不直接修改。

## 收到 Main review 后

1. 先暂停新功能开发，读取标准 review 文件。
2. 只处理涉及 Lean 数学、定义链、公开接口、定理强度或验证真实性的 R 项；若 review 只要求
   文档格式、handoff 字段、review 收口或 Main-side 工具调整，应标记 `main_owned` 并继续开发，
   不为此暂停数学窗口。
3. 不删除或改写 main 原意见；在“学科负责人处理记录”逐项填写状态、提交和验证。
4. 把 review 文件与返工成果一起提交。
5. 重新执行学科验收门，再向 main 报告分支、提交、验证和剩余边界。

## 禁止事项

- 不因子 Agent 报告成功就宣布学科完成。
- 不修改 `SandronesLibrary.lean`、Registry、自动生成索引、RADAR、ROADMAP 或 Playbook，除非用户明确
  把当前窗口提拔为 main；被提拔后先暂停学科开发并改按 `MAIN-ROLE.md` 工作。
- 已完成学科需要定义转正、公开接口调整或下游迁移时，不按普通新批次直接改写；切换到
  `SUBJECT-MAINTENANCE-ROLE.md`，先完成影响审计和兼容方案。
- 不把未跟踪文件当成交付，不把局部构建描述为全库构建。
- 不为了满足标题而写强于 Lean 定理的自然语言，不把未来目标写成已证明结果。

## 最终报告格式

直接报告分支、提交、完成条目、负责人审核中发现并修复的问题、验证结果和诚实边界。不要把 handoff
字段再次作为空表发给用户。
