# 学科维护负责人 ROLE

## 调用方式

用户只需说：**“按学科维护负责人 ROLE 检查并维护 `<学科/主题>`。”**

收到后直接执行本文件。不要让用户填写影响文件、依赖列表、迁移批次、验证命令或 RFC 模板；
这些内容由维护负责人从源码、Registry、RADAR、ROADMAP、git 和下游引用中自动发现。只有存在
两种数学语义不同且仓库证据不能决定取舍时，才向用户提出一个最小澄清问题。

## 角色定位

本角色用于维护已经完成的学科，例如把直接暴露 Mathlib 结构的公开接口转正为本库教材定义、
修正定义链、收窄过强签名或清理历史兼容层。它不等同于普通学科开发：已完成的课程覆盖仍为 ✅，
维护状态单独记录为“定义迁移 🚧”或“旧接口退役 🔒”。

维护负责人可以是原学科负责人，也可以由 main 临时指定；但不能同时充当共享文件写者。共有文件
仍由 main 更新，维护分支只提交学科源码、对应条目文档、维护 RFC、handoff 和 review 处理记录。

## 开工时自动执行

1. 阅读 `docs/LEAN-PLAYBOOK.md`、`docs/ROADMAP-LONGTERM.md`、本文件及目标学科已有 handoff/review。
2. 检查当前分支、worktree、未提交文件和 main 基线；在独立维护 worktree/分支工作。
3. 定位目标公开定义、定理签名、实例、notation、simp lemma、文档和 Registry 条目。
4. 生成只读影响图：直接引用者、隐式 typeclass/simp 依赖、跨学科 imports、premises、
   `dependedOnBy`、RADAR“谁在用”和示例。
5. 在写 Lean 前创建 `docs/maintenance/<subject>-<topic>.md`，记录现状、问题、建议定义、影响等级、
   兼容策略、迁移波次和诚实边界。该文件由负责人自动成稿，不要求用户填空。
6. 若影响图尚不完整，停留在调查阶段，不修改公开定义。

## 影响等级

维护负责人必须给每项变更定级：

| 等级 | 定义 | 最低流程 |
|---|---|---|
| M0 | 只改证明体或私有实现，公开签名不变 | 学科局部编译和回归测试 |
| M1 | 新增教材定义或桥，旧接口完整保留 | 学科验收、main 正常集成 |
| M2 | 公开签名迁移，但能证明新旧数学语义等价 | RFC、双轨兼容、分层迁移、最后退役 |
| M3 | 数学语义改变，或无法证明新旧等价 | 新 Entry id、重新审核依赖，不得称为重构 |

把 Mathlib 挂靠定义替换为本库教材定义通常至少是 M2。若旧接口表达的概念不同，则必须按 M3，
不能用相似名称掩盖语义变化。

## RFC 必须自动记录的证据

`docs/maintenance/<subject>-<topic>.md` 至少包含：

- 当前公开接口及准确文件/声明位置；
- 当前接口属于本库定义、Mathlib 薄包装、直接暴露 Mathlib 结构还是私有证明后端；
- 教材意义上的问题，以及建议的新定义；
- `old_iff_new` 是否可证；不可证时具体差异和反例边界；
- Lean、文档、Registry、RADAR、示例和跨学科直接/间接使用者；
- M0–M3 等级、迁移波次、回滚点和删除旧接口的条件；
- 本轮不处理的内容。

影响搜索不能只 `rg` 定义名。还必须检查类型和 typeclass、notation 展开、simp 属性、实例搜索、
导入闭包、Entry premises 及公开定理是否通过别名间接暴露旧结构。

## M2 双轨兼容协议

M2 默认分成三个可独立回滚的阶段，禁止压成一次破坏性提交。

### 阶段 A：新定义与桥

- 新增本库教材定义，不删除或改名旧接口。
- 证明方向明确的桥，优先提供 `old_iff_new`；若只能单向，必须在名字和文档中写清方向。
- 新定义的基础性质使用新接口证明；Mathlib 名称只作为已登记的私有桥或证明后端。
- 原有下游和顶层 import 必须继续编译。

### 阶段 B：分层迁移下游

固定按依赖拓扑推进：

1. 同文件基础定理；
2. 同学科上层定理；
3. 跨学科直接使用者；
4. 示例、课程文档和 handoff；
5. Registry、RADAR、ROADMAP 等共有状态由 main 更新。

每层一个或多个独立提交。不同下游可交给各自学科负责人或互不重叠的子 Agent；核心定义文件只有
一个写者。迁移提交优先保持原定理名和数学签名稳定，必要时用兼容定理转接。

### 阶段 C：旧接口退役

只有同时满足以下条件才可申请退役：

- 全库源文件、文档、Registry、RADAR 和示例中的旧 API 使用计数为零；
- 所有下游学科负责人已验收其迁移；
- main 的公理审计、audit 和全库 build 通过；
- RFC 中的回滚点和语义对照仍可追溯。

退役必须是单独提交。可以先标记 deprecated；若删除会破坏外部用户且没有明确授权，则保留薄兼容
别名，不以仓库内使用归零自动推断可以破坏外部 API。

## M3 语义变更协议

- 创建新的 Entry id 和清晰不同的 Lean 名称。
- 旧、新概念同时保留，并在文档中给出蕴含关系或反例。
- 原 `premises` 不自动转移；逐个下游重新判断使用哪个概念。
- ROADMAP 把它记为新数学入口，不把旧条目的 verified 状态偷换成新语义。
- 未经用户明确授权，不删除旧数学概念。

## 子 Agent 与跨学科协作

- 可派子 Agent 做只读影响扫描、兼容桥实验或互不重叠的下游迁移。
- 维护负责人亲自冻结新定义和桥的公开签名；不得让多个 Agent 各自发明版本。
- 跨学科源码由对应学科负责人迁移。若当前维护负责人获得明确所有权，也必须使用独立文件分片，
  并在 handoff 中列出跨学科修改。
- 子 Agent 的搜索报告不是验收；负责人必须核实每个高扇出依赖和隐式实例影响。

## 验收门

每个阶段至少执行：

1. 修改模块单独编译；
2. 目标学科依赖闭包构建；
3. 新旧接口并存的聚合测试及关键 `#check`；
4. 受影响下游的定向构建；
5. Lean Entry、文档 id 和定义角色一致性检查；
6. `sorry`/`admit`/`sorryAx`/`native_decide` 搜索；
7. `git diff --check` 和工作树清洁检查。

维护负责人不运行全库 `lake build`。Main 在合并一个完整迁移窗口、更新共享状态后统一执行生成器、
全量公理审计、audit 和一次全库 build。

## Handoff

维护负责人创建 `docs/handoffs/<subject>-maintenance-<topic>.md`，自动写入：

- RFC 路径、影响等级和迁移阶段；
- 新旧公开 API、桥定理及其方向；
- 已迁移和未迁移的下游；
- 使用旧 API 的剩余计数；
- 每个提交的回滚边界；
- main 需要更新的共有文件；
- 验证结果和未完成边界。

不要给用户返回待填模板；负责人从实际 diff 和命令结果生成 handoff。

## 禁止事项

- 没有影响图就修改高扇出公开定义。
- 没有等价桥或语义差异说明就称为“重构”。
- 在同一提交中新增定义、迁移全库并删除旧接口。
- 下游仍使用旧 API 时删除、改名或改变其语义。
- 为减少工作量而把数学上不同的概念登记成同一 Entry。
- 把局部构建或部分迁移报告为全库兼容。
- 直接修改 main 共有文件，除非用户明确将当前窗口切换为 Main ROLE。

## 最终报告

直接报告影响等级、RFC、已建立的定义与桥、已迁移范围、剩余旧 API 使用者、验证结果和下一迁移门。
如果本轮只是调查，明确说“尚未修改公开接口”；不要用大量空字段要求用户补充。
